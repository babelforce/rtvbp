# Public documentation reading experience

**Status:** accepted · **Story:** R-42 · **Parent:** [Documentation generation](docs-gen.md)

## Decision

Treat the documentation as a product surface with three progressive entry points: **Understand**
explains the protocol model, **Build** routes by implementation boundary, and **Reference** exposes
the generated contract and proven flows. A manual top-level sidebar owns that hierarchy while each
generated catalog remains autogenerated below its stable boundary.

The docs introduction becomes a compact gateway rather than another reference article. It states
the voice/application relationship, links to the zero-backend lab, routes to every SDK and the wire
contract, and names released distributions. Deeper hand-written guides retain ordinary Markdown so
their source stays easy to maintain.

## Presentation boundary

Shared theme CSS owns typography, content width, headings, tables, code, admonitions, Mermaid,
breadcrumbs, sidebars, table of contents, pagination, edit links, dark mode, and responsive behavior.
Generated MDX is never changed to obtain a visual result. Hand-written pages may use small semantic
HTML/MDX components only when they convey navigation or status that plain prose cannot express as
clearly.

The interactive `/try` implementation is not restyled by this work. Global tokens may be refined,
but selectors for documentation chrome are scoped under Docusaurus docs classes so the phone remains
visually and behaviorally unchanged.

## Accessibility and resilience

Reading measure remains bounded while wide tables and code scroll inside their own regions instead
of widening the page. Focus is obvious, skip navigation remains first-class, touch targets are at
least 44 pixels where practical, and motion is removed under `prefers-reduced-motion`. Color is never
the only active-state signal. Both themes use the same hierarchy and contrast intent.

Static HTML contains the page title, summary, and navigation before hydration. The site has no
runtime dependency beyond its existing public font request, no analytics, no private endpoint, and
no new credential surface.

## Proof

A Chrome acceptance test starts the production static build and checks the docs gateway, manual
sidebar hierarchy, guide and generated reference pages, keyboard focus, theme switch, contained
table/code overflow, and desktop/mobile geometry. The ordinary Docusaurus build remains the source
of the tested artifact.
